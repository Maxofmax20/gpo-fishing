# OCR Audit Pipeline

Turns the captured GPO dataset into an auditable map between **screenshots,
text, the GPO ontology, stored labels, and evidence** — so a human can open one
report and answer:

> What did the game actually write? Which image proves it? What did our dataset
> call it? What does the KB know about that name? Is it an entity, an alias, an
> OCR error, a compound name, an unknown concept, or a conflict? How many times?
> Across how many sessions and days? Which exact screenshots should I inspect
> first?

The purpose is **not** to make OCR decide what a fish is. It is to make every
text finding traceable, reviewable, and impossible to act on automatically.

---

## Quick start

```bash
pip install -r ml/gpo_ocr_audit/requirements.txt

# Regenerate the KB export from the real Rust knowledge base (read-only).
cd src-tauri && cargo run --example kb_export -- ../ml/gpo_ocr_audit/kb_export.json && cd ..

# Run the audit over the whole dataset.
python -m ml.gpo_ocr_audit

# Run the tests (no pytest needed).
python -m ml.gpo_ocr_audit.tests
```

Options:

```text
--dataset-root PATH     dataset dir (default %APPDATA%/gpo-autofish/datasets/gpo-vision/v1)
--out PATH              output dir (default reports/ocr_audit)
--workers N             OCR worker processes (default cores-2, max 8)
--limit N               debug only; a limited run is flagged as invalid in the report
--no-model              skip the shipped-model cross-check column
--no-contact-sheets     skip contact-sheet rendering
--query TEXT            search the generated index, e.g. --query "crimson snapper"
```

**CPU only.** No CUDA, no GPU, no torch. `rapidocr-onnxruntime` ships its models
inside the wheel, so there is no model download at audit time and no network
access once installed.

## Layout

| file | role |
|---|---|
| `schemas.py` | record types + the audit taxonomy (two independent axes) |
| `text_normalizer.py` | port of the Rust `canon` folding, plus registered OCR repairs |
| `ontology_matcher.py` | text → candidate KB entities, **never** to an answer |
| `ocr_engine.py` | independent OCR, mandatory image hashing, sha256-keyed cache |
| `gpo_correlator.py` | read-only join against labels / reviews / splits / model |
| `ocr_audit.py` | orchestrator; owns the single primary verdict |
| `report_generator.py` | markdown reports, contact sheets, SQLite search index |
| `__main__.py` | CLI |
| `tests/` | 49 tests, dependency-free runner |
| `kb_export.json` | generated by `cargo run --example kb_export` |

### Why `kb_export.json` exists

The knowledge base lives in Rust (`core::knowledge::build_bundled`). Loading it
from Python any other way would mean maintaining a second ontology in Python —
precisely the class of bug `FISH_VOCAB.txt` was introduced to eliminate. So a
Rust **example** target (not a binary, not a library function, unreachable from
the app at runtime) serialises the live KB, and the audit asserts that its
`fish_vocab` matches `FISH_VOCAB.txt`.

## Two independent axes

Collapsing these would hide exactly the rows a human needs.

**`image_category`** — what the frame *is*:
`FISH_DROP`, `FRUIT_DROP`, `BAIT_DROP`, `UI`, `WAITING`, `BITE`, `BANNER`,
`UNKNOWN`, `OCR_FAILURE`.

**`audit_status`** — exactly one per image, chosen by precedence:

| # | status | meaning |
|---|---|---|
| 1 | `OCR_UNREADABLE` | no text recovered |
| 2 | `NON_FISH` | a known banner template, or UI text on a frame that never shows an entity |
| 3 | `COMPOUND_AMBIGUOUS` | two or more whole-word canonical entities |
| 4 | `UNKNOWN_ENTITY` | a real name the KB cannot account for, wholly or in part |
| 5 | `OCR_CONFLICT` | exactly one candidate, and it is not the stored label |
| 6 | `CONFIRMED_MATCH` | one candidate equal to the stored label, exact/normalized |
| 7 | `ALIAS_MATCH` | as above via a declared alias |
| 8 | `OCR_VARIANT_MATCH` | as above via a registered repair or confusable fold |
| 9 | `NO_DECISION` | a single candidate but nothing to compare against |

**Ambiguity outranks conflict.** When a name is compound there is no single answer
to compare the stored label against, so the row is ambiguous regardless of what
was stored. Collapsing that would recreate the original bug.

---

## The rule that matters

> A name that matches **zero** or **two-or-more** canonical entities is **not**
> resolved.

`Crimson Snapper` contains `crimson` and `snapper`, both canonical. It yields
`COMPOUND_AMBIGUOUS` with both candidates and picks neither.

Three further refusals, each a mistake this project has already made once:

- **A fragment is not a match.** `tiger` occurs inside `tigerfin`. That is recorded
  but never resolved, so `Exotic Tigerfin` stays `UNKNOWN_ENTITY` instead of
  becoming `fish:tiger`.
- **A partly-explained name is not a match.** `golden polka puffer` contains the
  real entity `golden`, but `polka puffer` is unknown, so the whole name is
  `UNKNOWN_ENTITY`.
- **A lossy fold is not an exact match.** `5hark` reaches `fish:shark`, but the
  pixels never said "shark", so it is reported as `CONFUSABLE`.

### Correction rules repair text, never the ontology

Every rule in `OCR_CORRECTION_RULES` is a **whole-token substitution**. No rule
may span whitespace, because a multi-token pattern could *splice* an entity name
across a word gap — which is the failure being guarded against.

So `tiserfin → tigerfin` is allowed (it repairs corrupt text so one concept
groups across OCR variants) and `tigerfin → tiger` is not. `tests/` asserts that
no excluded concept can be turned into a known entity by any rule.

## Output

Written to `reports/ocr_audit/`:

| file | answers |
|---|---|
| `evidence.jsonl` | the complete, replayable per-image analysis |
| `provenance.json` | dataset / KB / OCR fingerprints and configuration |
| `summary.md` | headline counts, confidence distribution, per-class clean share |
| `class_quality.md` | per-class: confirmed, conflict, compound, unknown, clean % |
| `compound_names.md` | names containing 2+ canonical entities |
| `unknown_entities.md` | **candidate ontology concepts** needing a decision |
| `conflicts.md` | rows where the text disagrees with the stored label |
| `sessions.md` | recurrence per session and per calendar day |
| `ocr_quality.md` | confidence distribution, rules fired, char disagreements |
| `agreement_matrix.md` | stored / model / OCR three-way comparison |
| `search_index.sqlite` | queryable concept → images, sessions, labels |
| `contact_sheets/` | grids of the actual source images, captioned |

Query the index:

```bash
python -m ml.gpo_ocr_audit --query "crimson snapper"
```

```sql
sqlite3 reports/ocr_audit/search_index.sqlite
SELECT concept, occurrences, sessions FROM concepts ORDER BY occurrences DESC LIMIT 20;
SELECT image_id, stored_entity_id, raw_ocr FROM evidence
  WHERE residual_text LIKE '%crimson snapper%';
```

## Guarantees

Enforced by tests in `tests/`, not only asserted in prose.

- **Read-only.** No dataset row, KB entity, `FISH_VOCAB.txt`, label, split,
  registry entry or game control is written. `tests/test_safety_and_determinism.py`
  parses the AST of every module and fails if a forbidden import or write appears.
- **Traceable.** Every evidence record carries the SHA-256 of the exact image
  bytes analysed. The test verifies recorded hashes against the files on disk.
- **Deterministic.** Evidence records contain no wall-clock field, and the OCR
  cache is keyed on `image_sha256 + engine fingerprint`, so caching cannot change
  the answer and a stale result cannot survive a configuration change.
- **TEST is sacred.** Split membership is *imported* from
  `gpo_train.dataset.fnv1a_session_split`, never re-derived. TEST rows appear in
  the reports for reporting only; nothing is tuned on them.
- **No fabricated data.** Every row traces to a real image. `--limit` runs are
  stamped as invalid in the emitted README.

---

## What this pipeline does **not** do

- **It does not create ontology entities.** Unresolvable names are reported as
  *candidate* concepts. Adding one is a separate, human-approved phase.
- **It does not change labels.** `labels.jsonl` is opened read-only; no
  `training_eligible` flag is written.
- **It does not train or promote anything.** The shipped `fish_v1` model is read
  only for the cross-check column.
- **It does not weaken a gate.** No threshold, review requirement, or split rule
  is touched.
- **It does not control the game.** The pipeline imports no input, macro, or
  controller module.
